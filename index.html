Guillermo Rauch

Introducing gdp-ts: Ghosts of Departed Proofs for TypeScript. gdp-ts is a library, linter and AI skill for safer API design. Under this contract, sensitive functions require 'proofs' that the caller performed an authorization check. The typechecker verifies these proofs at compile time, preventing your team and agents from shipping catastrophic security (and other kinds of) bugs. While these patterns have existed for quite some time, especially in ecosystems like Haskell, ① human code review and ② cognitive and syntactic overhead made these solutions niche. The situation is now inverted. Agents are writing more code than we can review, and they *thrive* in tight loops with hard constraints that would frustrate us. We see this with the rise of Rust, borrow checker, code aesthetics debate and all. The README and examples model a real-world Vercel API product constraint: changing the password on a Project requires a proof of a certain role + a certain entitlement. Thanks to Matt Noonan and Ollie Charles for their research in this space. https://t.co/eRWdiMvQ2V

隆重介绍 gdp-ts：面向 TypeScript 的「逝者之证」（Ghosts of Departed Proofs）。 gdp-ts 是一个库、一个 linter，也是一项 AI 技能，用于更安全地设计 API。在这套契约下，敏感函数要求调用方提供「证明」，证明其已执行过授权检查。 类型检查器会在编译期验证这些证明，从而阻止你的团队和 Agent 发布灾难性的安全（以及其他类型的）Bug。 这类模式其实早已存在，尤其在 Haskell 等生态中，但 ① 人工代码审查 ② 认知与语法上的额外负担，让这些方案一直很小众。 如今局面反转了。Agent 写出的代码量已远超我们能审查的规模，而它们恰恰在那些会让我们抓狂的、带硬约束的紧密循环中如鱼得水。Rust 的崛起、借用检查器、代码美学之争等等，都印证了这一点。 README 和示例模拟了一个真实世界的 Vercel API 产品约束：修改某个 Project 的密码，需要提供特定角色 + 特定权益的证明。感谢 Matt Noonan 和 Ollie Charles 在这一领域的研究。

Aaron Levie

@levie
@Box CEO —— 你的业务存续于内容之中，用 AI 释放它的价值

A decent amount of agent adoption and deployment is bottlenecked by being able to test, tune, and optimize agents on “real” work environments. The files agents need to access, the CRM environments, email, and more. It’s impossible to know how agents are performing if you don’t understand how well they’re executing on your evals and how they’ll perform in the future with a model change or workflow upgrade. Every enterprise has to do this 1 by 1 right now, which is obviously slow and tedious. Every enterprise is going to have someone managing evals, infrastructure for building and running evals and simulated environments, and more. Huge space.

相当一部分 Agent 的采用与部署，瓶颈在于能否在「真实」工作环境中对 Agent 进行测试、调优和优化——包括 Agent 需要访问的文件、CRM 环境、邮件等等。 如果你不清楚 Agent 在你的评测集上执行得如何，也不清楚在模型更换或工作流升级后它们将表现如何，那你根本无法知道 Agent 的实际表现。目前每家企业都得一个一个地做这件事，显然既慢又繁琐。 未来每家企业都会有人专门负责评测、负责构建和运行评测与模拟环境的基础设施，以及更多相关工作。这是一个巨大的市场。
